Demerzel — Architecture & Design

2026-09-22 · repo github.com/a-mad-av8r/demerzel (fork of gpt-load v2 @1f615d83, MIT) · plan-of-record in kos-infra discovery track · Cortex platform: github.com/Kaidera-AI/cortex (install guide for team members without it)

Demerzel is a local-first LLM gateway: one endpoint on your laptop at http://127.0.0.1:3001/v1, with a pool of accounts behind every provider — several Claude or Codex subscriptions, API-key collections, cloud providers — with deterministic serial failover between them. This page answers: what we borrow from where · how the modules fit · why any module can be replaced later · how it ships to the team.

The one-way knowledge rule is the whole trick. An executor knows its provider's wire protocol and one account's credentials — nothing about routing strategy. The selector knows pools and quota state — nothing about HTTP. The vault knows secrets — nothing about any of it. Knowledge only flows down, so any layer can be swapped without its neighbors noticing.
Design-review finding (internal, 2026-09-22): the stage-1 → stage-2 order can mismatch when stage 1 picks a model no account in the pool can serve (404/403 after policy fires). Fix: stage 1 selects from the served-model set (the union of models the pool's accounts actually expose), and stage 2 answers "which account that can serve this model" — the pool is the capability source of truth, not the catalog.

3 · Request path — two stages

request
STAGE 1 — model policy
L1 picks what to ask: fixed model, or escalation/stage/classifier/prefill
STAGE 2 — account pool
L0 picks whom to ask as: eligibility → cooldown → quota → cursor → lease → execute
provider API

Stage 2 is policy-armored: no model-router result, cache hint, or escalation decision can bypass account eligibility, cooldown, or a permanent-denial identity. Stage 1 picks what; stage 2 picks as whom; neither crosses.

4 · Serial failover — one account at a time

ACTIVE (N)
cursor on account N; all traffic; reserve threshold armed
CLEAN ERROR?
transient 5xx/network → short cooldown, retry same account. Only a classified 429/usage-cap moves on.
LIMIT HIT → ADVANCE (N+1)
persist reset + cooldown; cursor moves; N+1 becomes active; no flapping back
FAILBACK
after N's reset + grace → probe with backoff (not once) → success → cursor home
…and on a timeline — a pool of two Claude subscriptions over a week:

Tue 19:15
grace passed → probe acct-1 ✓
cursor=1
Wed…
acct-1 active again
probes with backoff, never flapping
  • Cursor is persisted — a restart doesn't reshuffle accounts.
  • Never estimate "low tokens" from local counts — only provider quota telemetry or a classified limit response moves the cursor.
  • Failback happens once per reset window, via probes with exponential backoff.

5 · Model-selection engine (Switchyard-pattern, ours)

NVIDIA NeMo Switchyard (Apache-2.0, pre-1.0) is a model-level router: it decides per agent step which model should answer — not which account. Demerzel brings its capability set in-house as our own Go module behind the stage-1 interface; the NVIDIA repo serves as a pinned evaluation oracle in M2 and never ships as a production dependency.

Escalation
cheap model first → escalate on persistent difficulty
Stage routing
model by workflow stage / recent tool activity
Classifier
a judge model picks the target
Prefill
predict success from inference-time signals

Benchmarks (labeled): official repo reports ~13–30% cheaper at 71–76% accuracy vs Opus baseline; a separate media-reported LangChain workload showed 74% cost cut / ~6pt accuracy drop. Neither is our acceptance target — the M2 spike on our own trace decides. Two-stage ordering stays explicit: model routing (stage 1) never bypasses account selection policy (stage 2).

6 · Swappability mechanics — the actual trick

  • Tiny interfaces we own. Donor code (CLIProxyAPI executors, Bifrost conversions) is adapted at the boundary — never imported deep. Replacing Bifrost with another converter touches one adapter file.
  • Pinned commits + ledger. VENDORING.md records donor, commit, paths, destination, license, modifications. Upgrading a donor = bump the pin + run that module's golden tests. Rebasing the gpt-load baseline is an explicit git merge upstream/main — never a silent package update.
  • One outbound edge. Only executors speak to the internet. Vault, selector, scheduler, UI make no network calls — a donor with phone-home habits is neutered by construction.
  • State lives in one place. SQLite + Keychain/libsecret key. The contract with reality (the DB schema) is narrow, so modules can be rewritten freely.

Every installer frontend verifies the same cosign-signed manifest before installing. The core never self-updates, never phones home. Secrets never ship in any artifact — each machine bootstraps its own vault and accounts. Release matrix is a proof gate: darwin/arm64 verified today; the other three targets are CI acceptance items.

8 · Phased build

  • M1 — fork + harden: VENDORING.md ✔ · fail-closed vault (Keychain/libsecret) · module interfaces · default-off outbound (incl. models.dev sync) · pinned deps. Accept: baseline receipt reproduces; 60s idle = zero egress.
  • M2 — account control plane + serial failover + Switchyard spike: registry UI/CLI · deterministic failover. Accept: scripted-429 failover test (persisted cursor, reset+grace, backoff-probe failback) + spike report (NVIDIA = eval oracle only).
  • M3 — providers: clean-key first, subscription OAuth executors flagged per compliance. Accept: golden transcripts + one live request per clean provider.
  • M4 — distribution: tap + bunx + tar/container, all verifying the signed manifest; Linux = macOS parity. Accept: install → service → health/auth → upgrade → rollback → uninstall on darwin/arm64 + linux/amd64.
  • M5 — our model-selection engine to production, gated on M2 spike evidence.

9 · Open questions

  • Vault master-key custody on macOS: Keychain via security CLI (recommended — no file on disk) vs age passphrase file (portable, but a file exists).
  • Subscription executors (Claude/Codex OAuth) in v1: ship disabled behind a flag with a compliance warning (recommended) vs enable day one.
