Demerzel — Architecture: how the modules fit and stay swappable

2026-09-22 · repo github.com/a-mad-av8r/demerzel (fork of gpt-load v2 @1f615d83, MIT) · plan-of-record in kos-infra discovery track

Demerzel is a local-first LLM gateway: one endpoint on your laptop at http://127.0.0.1:3001/v1, with a pool of accounts behind every provider — several Claude or Codex subscriptions, API-key collections, cloud providers — with deterministic serial failover between them. Three questions, answered visually: what we borrow from where · how the modules fit · why any module can be replaced later.

The one-way knowledge rule is the whole trick. An executor knows its provider's wire protocol and one account's credentials — nothing about routing strategy. The selector knows pools and quota state — nothing about HTTP. The vault knows secrets — nothing about any of it. Because knowledge only flows down, any layer can be swapped without its neighbors noticing.

3 · The two-stage request path

request
STAGE 1 — model policy
L1 picks what to ask: fixed model, or escalation/stage/classifier/prefill (our Switchyard-pattern engine)
STAGE 2 — account pool
L0 picks whom to ask as: eligibility → cooldown → quota → cursor → lease → execute
provider API

Stage 2 is policy-armored: no model-router result, cache hint, or escalation decision can bypass account eligibility, cooldown, or a permanent-denial identity. Stage 1 picks what; stage 2 picks as whom; neither ever crosses.

4 · Serial failover, precisely

ACTIVE (N)
cursor on account N; all traffic; reserve threshold armed
LIMIT HIT
classified 429 / usage-cap, or provider quota telemetry < reserve → persist reset + cooldown
ADVANCE (N+1)
cursor moves; N+1 becomes active; no flapping back
FAILBACK
after N's reset + grace → one probe → success → cursor home
What makes it deterministic (and testable):
  • Never estimate "low tokens" from local counts — only provider quota telemetry or a classified limit response moves the cursor.
  • Cursor is persisted — a restart doesn't reshuffle accounts.
  • Failback happens once, after reset + grace, via a single probe — not on whichever request arrives next.

5 · Swappability mechanics — the actual trick

  • Tiny interfaces we own. Donor code (CLIProxyAPI executors, Bifrost conversions) is adapted at the boundary — never imported deep. Replacing Bifrost with another converter touches one adapter file.
  • Pinned commits + ledger. VENDORING.md records donor, commit, paths, destination, license, modifications. Upgrading a donor = bump the pin + run that module's golden tests. Rebasing the gpt-load baseline is an explicit git merge upstream/main — never a silent package update.
  • One outbound edge. Only executors speak to the internet. Vault, selector, scheduler, UI make no network calls — a donor with phone-home habits is neutered by construction.
  • State lives in one place. SQLite + Keychain/libsecret key. The contract with reality (the DB schema) is narrow, so modules can be rewritten freely.

6 · Distribution (your other computers + the team)

CI releasecross-build matrix · cosign sign + SBOM · release.json.sig

Every installer frontend verifies the same cosign-signed manifest before installing. The core never self-updates, never phones home. Subscription tokens never ship in any artifact — each machine bootstraps its own vault and accounts. Release matrix is a proof gate: darwin/arm64 verified today; darwin/amd64, linux/amd64, linux/arm64 are CI acceptance items, not promises.

7 · Phased build

  • M1 — fork + harden: VENDORING.md ✔ · fail-closed vault (Keychain/libsecret) · module interfaces · default-off outbound (incl. models.dev sync) · pinned deps. Accept: baseline receipt reproduces; 60s idle = zero egress.
  • M2 — account control plane + serial failover + Switchyard spike: registry UI/CLI · deterministic failover. Accept: scripted-429 test (persisted cursor, reset+grace, single-probe failback) + spike report (NVIDIA = eval oracle only).
  • M3 — providers: clean-key first, subscription OAuth executors flagged per compliance. Accept: golden transcripts + one live request per clean provider.
  • M4 — distribution: tap + bunx + tar/container, all verifying the signed manifest; Linux = macOS parity. Accept: install → service → health/auth → upgrade → rollback → uninstall on darwin/arm64 + linux/amd64.
  • M5 — our model-selection engine to production, gated on M2 spike evidence.

8 · Open questions

  • Vault master-key custody on macOS: Keychain via security CLI (recommended — no file on disk) vs age passphrase file (portable, but a file exists).
  • Subscription executors (Claude/Codex OAuth) in v1: ship disabled behind a flag with a compliance warning (recommended) vs enable day one.
